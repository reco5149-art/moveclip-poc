# 개선 효과 검증 결과

문제정의서 5장에서 세운 성공 기준을 실제로 달성했는지 채점한다.

## 1. 검증을 어떻게 설계했나

정확도를 채점하려면 **정답이 있는 영상**이 필요한데, 회원이 나온 실제 촬영본은 공개 저장소에 올릴 수 없다.
그래서 **세트 구성(반복 횟수·휴식 길이)을 내가 지정해서 만든 합성 영상**을 테스트 자산으로 썼다.

- 실제 인물 사진을 분할해 골반~무릎 구간을 프레임마다 눌러 스쿼트 동작을 만든다 → 픽셀이 진짜 사람이라 YOLO가 정상 검출
- 세트 구성이 곧 정답 라벨 (`data/sample_workout_truth.json`)
- 재현: `python tools/make_sample.py` → `python main.py data/sample_workout.mp4` → `python tools/evaluate.py`

| 세트 | 구간 | 반복 | 반복 주기 |
|---|---|---|---|
| 1 | 5.0 – 21.0s | 8회 | 2.0초 |
| 2 | 27.0 – 36.6s | 6회 | 1.6초 |
| 3 | 41.6 – 55.6s | 10회 | 1.4초 |

전체 59.6초 / 1280x720 / 30fps, 설명·휴식 구간 15초 포함.

> **이 검증의 한계를 먼저 밝힌다.** 합성 영상은 배경이 깨끗하고, 인물이 1명이고, 반복 주기가 완벽하게 일정하다. 실제 수업 영상보다 훨씬 쉬운 조건이다. 아래 숫자는 **상한선**으로 읽어야 하며, 본인 촬영본으로 한 번 더 검증해야 한다(→ 5장).

### 2-2. 처리 시간

**① 테스트 영상(59.6초) 실측**

| 구분 | 시간 |
|---|---|
| PoC 자동 처리 | **73초** (포즈 30.4s / 반복검출 0.02s / 음성인식 0.06s(무음) / 렌더 42.0s) |
| 그중 사람이 붙어 있어야 하는 시간 | **0초** |

**② 실제 병목 구간(30분 촬영본)으로 환산**

60초짜리 영상은 수작업으로도 금방 끝난다. 문제가 생기는 건 30분짜리 수업 촬영본이므로, 실측값을 그 길이로 환산해 비교한다.

| | 수작업 | PoC |
|---|---|---|
| 탐색 (쓸 구간 찾기) | 20~30분 | 0분 |
| 컷·세로변환·자막·카드뉴스 | 5~10분 | 0분 |
| 기계 처리 시간 | — | **약 18분** (포즈 15.2분 + 음성인식 2.3분 + 렌더 0.7분) |
| 후보 검토·다듬기 | — | 3~5분 |
| **사람이 붙어 있는 시간** | **25~35분** | **3~5분** |

> **이 표를 읽는 법.** 기계가 도는 총 시간(18분)은 수작업(25~35분)보다 조금 짧을 뿐이다. **진짜 차이는 그 18분 동안 사람이 자리에 없어도 된다는 것이다.** 촬영 후 걸어두고 다른 일을 하면 된다. 문제정의서가 정의한 병목은 '총 소요 시간'이 아니라 '내가 붙어 있어야 하는 시간'이었다.
>
> **아직 실측이 아닌 값:** 수작업 25~35분은 체감 추정치다. 본인 촬영본으로 수동 편집을 한 번 스톱워치로 재서 이 칸을 채워야 비교가 완성된다(→ 문제정의서 5-3). PoC 쪽 숫자는 전부 실측이다.
> **환산의 한계:** 포즈 추출은 영상 길이에 비례하지만 렌더링은 숏츠 개수에만 비례한다. 실제 30분 영상을 한 번 돌려 확인해야 한다.

## 3. 실제 코칭 영상 검증 ★ 핵심

합성 영상만으로는 부족해서, **실제 크로스핏 코칭 영상**(에어 스쿼트 플레이트 드릴, 107초 / 1920×1080 / 한국어 음성)으로 다시 돌렸다.
이 영상에는 원본 자막이 화면에 박혀 있어서, **그 자막을 음성인식 정답으로 쓸 수 있었다.**

### 3-1. 정답 라벨 만들기

합성 영상과 달리 정답이 주어지지 않으므로, **명시적 규칙**으로 라벨을 만들고 프레임을 눈으로 대조해 검증했다.

> 규칙: 무릎각이 110° 아래로 내려갔다가 150° 위로 올라오면 1회.

| 구간 | 실제로 무슨 장면인가 | 정답 |
|---|---|---|
| 5.4 – 10.4s | 플레이트 집고 자세 잡기 | 준비 동작 (스쿼트 아님) |
| 16.5 – 26.5s | 서서 설명 + 플레이트 들어 보이기 | **0회** |
| 35.4 – 55.4s | 시범 스쿼트 | **3회** |
| 62.2 – 97.4s | 본 드릴 스쿼트 | **5회** |

### 3-2. 1차 결과 — 오검출 발견

| 검출 구간 | 검출 반복 | 정답 | 판정 |
|---|---|---|---|
| 0.0 – 8.6s | 2회 | 준비 동작 | △ |
| **17.4 – 25.4s** | **3회** | **0회 (서서 설명)** | ❌ **오검출** |
| 33.6 – 51.2s | 2회 | 3회 | △ |
| 55.0 – 102.0s | 5회 | 5회 | ✅ |

원인을 파고들다 **버그 하나와 설계 결함 하나**를 찾았다.

**버그: 자기상관에서 주기를 잘못 뽑고 있었다.**
모든 구간의 주기가 0.4초(허용 범위의 최솟값)로 보고되고 있었다. 부드러운 신호는 lag이 작을수록 자기상관이 높아서, 범위 내 **최댓값**을 취하면 항상 최소 lag이 뽑힌다. 진짜 주기는 자기상관의 **국소 최대(peak)** 위치다. 합성 영상에서는 이 버그가 드러나지 않았다 — 반복이 워낙 규칙적이라 결과가 우연히 맞았다.

**설계 결함: 코칭 영상에 자기상관은 애초에 안 맞는다.**
버그를 고치고 보니 정작 본 드릴 구간의 주기성 점수가 0.00이었다. 실제 반복 간격을 재보니 **10.6초 / 6.2초 / 9.2초 / 4.8초** — 설명하느라 간격이 제멋대로다. 운동 영상은 메트로놈이 아니다. 주기성으로 신호를 고르면 정작 스쿼트를 놓친다.

### 3-3. 도메인에 맞춘 튜닝

주기성 대신 **가동범위 × 관절 우선순위**로 신호 선택 기준을 바꿨다.

```python
SIGNAL_PRIORITY = {"무릎각": 1.00, "고관절각": 0.95, "골반높이": 0.80,
                   "팔꿈치각": 0.55, "손목높이": 0.50}
pick = PRIORITY × min(1, ROM/60) × (0.6 + 0.4 × 주기성)
```

**왜 하체 신호를 우선하는가** — 코치는 설명하는 내내 팔을 쓴다. 플레이트를 들어 보이고, 손으로 방향을 가리킨다. 그래서 상체 신호는 '운동이 아닌 구간'에서도 크게 흔들린다(위 17–25초 오검출의 정체가 바로 이것이다). 반면 무릎·고관절은 실제로 운동할 때만 움직인다. **이건 논문에서 가져온 규칙이 아니라 내 도메인을 알아서 세운 규칙이다.**
함께 신호별 최소 가동범위 기준도 넣었다(각도 25~30°, 위치 15~20%).

### 3-4. 개선 전 / 후

| | 개선 전 | 개선 후 |
|---|---|---|
| 설명 구간(17–25초) 오검출 | **3회 검출** ❌ | **검출 안 함** ✅ |
| 본 드릴 반복 수 (정답 5회) | 5회 ✅ | 5회 ✅ |
| 동작 종류 분류 | 상체·전신·하체 뒤섞임 ❌ | **3개 구간 모두 "하체 반복 동작(스쿼트·런지 계열)"** ✅ |
| 합성 영상 회귀 | — | 재현율 1.00 / 반복 3/3 유지 ✅ |

최종 검출 결과:

| 검출 구간 | 반복 | 분류 | 정답 대비 |
|---|---|---|---|
| 53.8 – 98.8s | 5회 | 하체(스쿼트·런지) | ✅ **정확** |
| 32.4 – 52.4s | 2회 | 하체(스쿼트·런지) | △ 3회 중 2회 (세 번째가 구간 경계에 걸림) |
| 0.0 – 9.8s | 2회 | 하체(스쿼트·런지) | △ 준비 동작을 세트로 인식 |

처리 시간: **107초 영상 → 254초** (포즈 72.8s / 음성인식 52.0s / 렌더 128.9s), 인물 검출률 93%.

### 3-5. 한국어 음성인식 실측 — 목표 미달 ❌

영상에 박힌 원본 자막 7문장을 정답으로 잡고 문자오류율(CER)을 쟀다.

| 정답 (영상 자막) | base | small |
|---|---|---|
| 자세를 한 번 먼저 보고 | 0.22 | 0.11 |
| 시선을 가능하면 구멍쪽으로 보고 | 0.43 | 0.14 |
| 엉덩이가 빠지면서 밀어주고 | 0.67 | 0.50 |
| 발목관절이 요렇게 되는게 아니라 | 0.21 | 0.50 |
| 처음에는 스쿼트가 안 되는 사람들이 | 0.27 | 0.13 |
| 웨이트를 갖고 멀어지면서 앉게 되면 | 0.67 | 0.67 |
| 더 쉽게 이 느낌을 찾을 수 있게 됩니다 | 0.27 | **0.00** |
| **평균 CER** | **0.39** | **0.29** |
| **문자 정확도** | **61%** | **71%** |

- **모델 업그레이드 효과 확인:** base → small로 바꾸니 정확도 61% → 71%. base에서 나타나던 무한 반복 붕괴("2.5.5.5.5.5…")도 사라졌다. 대가는 모델 1.3GB와 처리 시간 30초 → 52초.
- **그래도 목표 미달.** 성공 기준은 '수정 필요 문장 20% 이하'였는데, 문장 단위로는 사실상 전부 손봐야 한다. 특히 도메인 고유명사가 통째로 깨진다 — "크로스핏" → "크스", "플레이트" → "플이트", "드릴" → "드".
- **파급 효과:** 카드뉴스 문구가 STT에서 나오므로 품질이 그대로 따라 내려간다. 실제 생성된 카드에 "다시 돌아니다", "크스 코치 김영 호입니다" 같은 문장이 올라갔다. **큐 선별 로직 자체는 제대로 작동했다** — "발 관절이 … 눌러준다는 느낌으로", "더 쉽게 이 느낌을 찾을 수 있게 됩니다" 같은 진짜 코칭 멘트를 골라냈다. 병목은 선별이 아니라 인식이다.

### 3-6. 실제 영상에서 새로 발견한 문제

**① 이중 자막** — 원본에 자막이 박혀 있으면 우리가 생성한 자막과 겹쳐서 화면에 자막이 두 겹으로 뜬다. **자막 넣기 전 원본(raw)으로 처리해야 한다.**

**② 세로 크롭이 원본 화면 텍스트를 자른다** — 9:16으로 자르면 원본의 좌우 자막·타이틀이 중간에 끊긴다("엉덩…", "충…"). 같은 이유로 raw 영상이 필요하다.

**③ 자막 덩어리가 너무 길다** — VAD가 20초짜리 발화를 한 덩어리로 묶어서 자막이 3줄로 나온다. 숏츠에는 부적합하다. 문장 단위 분할이 필요하다.

## 4. 실패 사례 (합성 영상)

### 실패 ① 분석 샘플링을 낮추면 빠른 반복이 무너진다 ⚠️ 가장 중요

처리 속도를 올리려고 분석 fps를 5 → 2로 낮춰봤다.

| 세트 | 반복 주기 | 정답 | 5fps | **2fps** |
|---|---|---|---|---|
| 1 | 2.0초 | 8회 | 8회 ✅ | 7회 |
| 2 | 1.6초 | 6회 | 6회 ✅ | **4회** ❌ |
| 3 | 1.4초 | 10회 | 10회 ✅ | **3회** ❌ |

반복 수 정확도 **1.00 → 0.33**으로 붕괴. 구간은 여전히 다 찾았지만(재현율 1.00) 숫자가 완전히 틀렸다.

**원인:** 1.4초 주기 동작을 2fps로 보면 반복 1회당 샘플이 2.8개뿐 — 샘플링 정리(Nyquist) 위반으로 신호가 접힌다.
**대응:** 분석 fps 5 이상을 기본값으로 고정. 빠른 종목(버피, 더블언더, 케틀벨 스윙)은 8fps 권장. **속도를 위해 fps를 낮추면 안 된다**는 걸 수치로 확인한 게 이 실험의 수확이다.

### 실패 ② 동작 종류 추정이 틀린다 — 합성 영상에서만 ❌ → ✅

합성 영상에서는 3개 세트 모두 스쿼트인데 "상체 밀기·당기기 계열"로 분류했다(0/3).
**그런데 같은 코드가 실제 영상에서는 3개 구간 모두 "하체 반복 동작(스쿼트·런지 계열)"로 정확히 분류했다.**

원인은 모델이 아니라 **테스트 자산**이었다. 합성 영상은 골반~무릎 구간을 눌러 스쿼트를 흉내 내는데, 그 자리에 걸쳐 있던 팔까지 같이 눌려서 팔꿈치각이 실제보다 크게 흔들린다. 진짜 스쿼트 영상에서는 무릎이 압도적으로 크게 움직이므로 제대로 잡힌다.

**교훈: 합성 데이터로 검증할 때는 "틀린 게 모델인지 테스트 자산인지"를 먼저 의심해야 한다.** 실제 영상을 돌려보기 전까지 나는 이걸 분류 로직의 결함으로 적어뒀었다.

### 실패 ③ 다중 인물 — 이번엔 버텼지만 조건부 ⚠️

그룹 수업 상황을 모사해 **두 번째 인물이 옆에서 서성이는 영상**으로 다시 돌렸다.

| 지표 | 단독 인물 | 2인 |
|---|---|---|
| 세트 재현율 | 1.00 | 1.00 |
| 반복 수 완전일치 | 3/3 | **3/3** |
| 자동 크롭 | 주 피사체 중앙 | **주 피사체 중앙 유지** |

주 피사체 선택(면적 × 신뢰도 + 직전 프레임 중심과의 연속성)이 제대로 작동했다.
**다만 이건 주 피사체가 더 크고 화면 중앙에 있었기 때문**이다. 회원과 코치가 비슷한 크기로 서 있거나 서로 교차하면 인물이 바뀔 수 있다. 문제정의서의 "PoC 범위: 단일 인물" 제약은 그대로 유효하다.

### 실패 ④ 한국어 음성인식 — 실제 영상에서 목표 미달 확정 ❌

합성 영상에는 음성이 없어 보류했던 항목인데, 실제 영상으로 재보니 **문자 정확도 71%(small 기준)로 목표 미달**이었다. 특히 운동 도메인 고유명사가 통째로 깨진다. 상세는 3-5 참조.

| # | 지표 | 목표 | 합성 영상 | **실제 영상** | 판정 |

| 2 | 반복 카운팅 정확도 | ±1회 80% 이상 | 100% | **본 드릴 5/5 정확**, 전체 3구간 중 1개 정확·2개 근사 | △ 부분 달성 |
| 3 | 세트 구간 재현율 | 0.8 이상 | 1.00 | **1.00** (운동 구간 3/3 검출, 설명 구간 오검출 0) | ✅ |

| 5 | 1회 산출물 | 숏츠 3 + 카드뉴스 1세트 | 숏츠 3 + 카드 9 + 캡션 3 | 동일 | ✅ |

**정직한 결론:**
- **핵심 가설은 검증됐다.** "쓸 구간을 기계가 찾아준다"는 실제 영상에서 작동한다. 설명·휴식은 걸러내고 운동 구간만 3개를 정확히 집어냈으며, 본 드릴의 반복 수는 5/5로 정확했다.
- **자막은 쓸 수 없는 수준이다.** 한국어 인식 정확도 71%로는 그대로 못 올린다. 이건 다음 단계의 1순위 과제다.
- **처리 시간은 목표(3분)를 넘겼다.** 107초 영상에 254초. 다만 그 시간 내내 사람은 자리에 없어도 된다.

## 6. 한계와 다음 스텝

### 지금 확실한 것 (실제 영상으로 확인)
- **설명·휴식 구간을 걸러내고 운동 구간만 찾아낸다.** 서서 말하는 9초 구간을 오검출하던 문제를 튜닝으로 잡았다.
- **본 드릴의 반복 수를 정확히 센다** (5/5). 반복 간격이 불규칙해도(4.8~10.6초) 작동한다.
- **동작 종류를 맞춘다** — 실제 스쿼트 영상 3구간 모두 하체 계열로 분류.
- 9:16 자동 크롭에서 인물이 프레임을 벗어나지 않는다.
- 카드뉴스 **큐 선별 로직**은 진짜 코칭 멘트를 골라낸다. (문장 품질은 STT에 종속)
- 문제정의서의 **탐색 병목은 해결됐다.** 사람의 역할이 '찾기'에서 '고르기'로 바뀌었다.

### 아직 안 되는 것 — 우선순위 순

| # | 한계 | 왜 남았나 | 다음 스텝 |
|---|---|---|---|
| 1 | **한국어 STT 정확도 71%** | whisper-small의 한계, 운동 용어 미학습 | whisper-medium 시험 → 도메인 용어 사전 확장 → 그래도 안 되면 자막은 반자동(초안+수정)으로 설계 변경 |
| 2 | **이중 자막·원본 텍스트 잘림** | 자막이 박힌 완성본을 입력으로 씀 | **자막 넣기 전 raw 영상을 입력**으로 고정. 워크플로우 규칙으로 해결 가능 |
| 3 | **자막 덩어리가 3줄로 길다** | VAD가 20초 발화를 한 덩어리로 묶음 | 발화를 문장 단위로 재분할, 숏츠용 2줄 제한 |
| 4 | 처리 시간 목표 초과 (107초→254초) | 렌더링이 절반, 프레임 단위 파이썬 처리 | ffmpeg 필터로 이관 → 수 초 수준 기대 |
| 5 | 준비 동작을 세트로 오인 | 플레이트 집는 동작도 무릎이 굽음 | 최소 반복 수·최소 ROM 상향, 또는 연속 3회 이상만 세트로 인정 |
| 6 | 마사지·통증케어 영상 미적용 | 주기 동작이 없음 | 발화 기반(STT→코칭 큐) 경로 분리 — 2단계 과제 |

| 8 | 수작업 기준선 미실측 | 비교 대상이 추정치 | 이 영상을 수동 편집하며 스톱워치 측정 |

### 실제 도입까지 필요한 것
- **데이터:** 자막 없는 raw 촬영본 10개(종목별 2~3개), 운동 용어 사전 100개
- **비용:** 0원 (전부 로컬 CPU, API 사용 없음). 모델 저장공간 1.5GB와 배치 처리 시간만 비용
- **운영:** 촬영 → raw 파일을 폴더에 넣기 → 자동 배치 → 아침에 후보 검토 (현재는 수동 업로드)
